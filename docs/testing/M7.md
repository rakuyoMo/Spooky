## 准备测试仓库

一份准备脚本在同一个目录里建立下面这些内容，本机与服务器使用同一份脚本：

- `history`：历史搜索、排序分组、提交详情、合并 Diff 与签名
- `refs`：侧边栏、引用与远端管理、同步、Branches Review、Reflog 与撤销；它的 `origin` 是 `远端 origin.git`，另一个工作区 `other` 用来在别处推送
- `rewrite`：反转、摘取、重置、检出版本、变基到别处与交互式变基；`origin` 是 `rewrite.git`
- `modules`：带子模块 `lib` 的仓库，子模块的远端是 `lib.git`，另一个工作区 `lib-other` 在子模块的远端上多推了一个提交
- `journey`：端到端流程；`origin` 是 `journey.git`，另一个工作区是 `journey-other`
- `镜像 mirror.git`：空的裸仓库，手动添加远端时使用
- `git`：忽略系统与用户全局配置的 Git 入口，后文的终端命令都经它执行
- `signing_ed25519`、`allowed_signers`：测试专用、不带口令的 SSH 签名密钥与只列这把密钥的 allowed signers 文件，只写进测试仓库的本地配置
- `pre-push`：必定失败的推送前钩子
- `auth-server.pl`：只监听本机回环地址、对任何请求都要求登录的 HTTP 服务，用来触发凭据询问

### 公共部分

```sh
m7_script="$(mktemp "${TMPDIR:-/tmp}/spooky-m7-prepare.XXXXXX")"

cat > "$m7_script" <<'PREPARE'
set -eu
umask 077

root="$1"
git="$root/git"

# 手动步骤同样经这个入口执行 Git，忽略系统与用户的全局配置
cat > "$git" <<'WRAPPER'
#!/bin/sh
export GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_SYSTEM=/dev/null GIT_CONFIG_NOSYSTEM=1
exec /usr/bin/git "$@"
WRAPPER
chmod 700 "$git"

# 提交日期从运行脚本的时刻往前推固定的天数
now="$(date +%s)"

# 若干天前的 Git 日期，再早一小时，当天的提交也不会晚于现在
days_ago() {
    printf '%d +0000' "$((now - $1 * 86400 - 3600))"
}

# 新建仓库并进入它；提交身份只写进这个仓库的本地配置
create_repository() {
    "$git" -c init.templateDir= init -q -b main "$root/$1"
    cd "$root/$1"
    "$git" config --local user.name 'Spooky Test'
    "$git" config --local user.email spooky@example.invalid
    "$git" config --local commit.gpgSign false
    "$git" config --local tag.gpgSign false
}

# 以指定的作者在若干天前提交暂存区
commit_as() {
    stamp="$(days_ago "$3")"

    GIT_AUTHOR_NAME="$1" GIT_AUTHOR_EMAIL="$2" \
        GIT_AUTHOR_DATE="$stamp" GIT_COMMITTER_DATE="$stamp" \
        "$git" commit -q -m "$4"
}

# 以若干天前的日期执行一条 Git 命令，用于合并与附注标签
git_at() {
    stamp="$(days_ago "$1")"
    shift

    GIT_AUTHOR_DATE="$stamp" GIT_COMMITTER_DATE="$stamp" "$git" "$@"
}

# 测试专用、不带口令的 SSH 签名密钥，allowed signers 文件只列这一把
ssh-keygen -q -t ed25519 -N '' -C spooky-m7-signing -f "$root/signing_ed25519"
printf 'spooky@example.invalid %s\n' "$(cat "$root/signing_ed25519.pub")" > "$root/allowed_signers"

# 当前仓库用这把密钥签名与校验，只写本地配置
use_signing_key() {
    "$git" config --local gpg.format ssh
    "$git" config --local user.signingkey "$root/signing_ed25519"
    "$git" config --local gpg.ssh.allowedSignersFile "$root/allowed_signers"
}

# 必定失败的推送前钩子放在仓库之外，同步一节再复制进去
printf '#!/bin/sh\necho "pre-push rejected this push" >&2\nexit 1\n' > "$root/pre-push"
chmod 700 "$root/pre-push"

# 只监听本机回环地址、对任何请求都要求登录的 HTTP 服务，15 分钟后自行退出
cat > "$root/auth-server.pl" <<'SERVER'
use strict;
use warnings;
use IO::Socket::INET;

alarm 900;

my $server = IO::Socket::INET->new(
    LocalAddr => '127.0.0.1',
    LocalPort => $ARGV[0],
    Listen => 5,
    ReuseAddr => 1,
) or die "listen: $!\n";

while (my $client = $server->accept) {
    # 读完请求头再回 401
    while (my $line = <$client>) {
        last if $line =~ /^\r?\n\z/;
    }

    print $client "HTTP/1.1 401 Unauthorized\r\n",
        "WWW-Authenticate: Basic realm=\"spooky\"\r\n",
        "Content-Length: 0\r\n",
        "Connection: close\r\n\r\n";
    close $client;
}
SERVER
PREPARE
```

printf '# 发布说明\n\n- 第一版\n' > '文档/发布 说明.md'

printf 'log\n' > log.txt
printf 'first\nsecond\nthird\n' > conflict.txt
"$git" add --all
commit_as 'Alice Example' alice@example.invalid 150 'Start the release notes'

# 240 个只改 log.txt 的提交，作者轮换，日期从 140 天前到 20 天前
i=1

while [ "$i" -le 240 ]; do
    printf 'entry %d\n' "$i" >> log.txt
    "$git" add log.txt

    case $((i % 3)) in
        0) author='Alice Example' email=alice@example.invalid ;;
        1) author='Bob Example' email=bob@example.invalid ;;
        *) author='Carol Example' email=carol@example.invalid ;;
    esac

    commit_as "$author" "$email" $((140 - i / 2)) "Update the log #$i"
    i=$((i + 1))
done

printf 'let star = "*"\n' > 'src/解析 器.swift'
"$git" add --all
commit_as 'Bob Example' bob@example.invalid 18 'Fix *star* parsing in 解析器'

# 作者是 Carol、提交人是 Release Bot
printf '# 发布说明\n\n- 第一版\n- 第二版\n' > '文档/发布 说明.md'
"$git" add --all
stamp="$(days_ago 15)"

GIT_AUTHOR_NAME='Carol Example' GIT_AUTHOR_EMAIL=carol@example.invalid \

   - None：两个合并提交都没有文件

4. 选中 “Fix \*star\* parsing in 解析器”，切到 Tree：
   - 根目录列出 `src`、`文档` 与各文件；目录逐层展开，`src` 下是 `解析 器.swift`
   - 右键 `解析 器.swift`，依次是查看这个版本的原文、Blame 与文件历史，在工作区恢复成这个版本、导出这个文件与把它归档成 zip，标题都写出文件名与短哈希

   - 选中它时，详情头部多出签名状态一行；关掉 Verify Signatures 后列表的按钮消失，详情的签名行仍在
   - 历史行里的标签标记可以点：`v2.1` 的弹窗是 Signature Good，`v2.0` 是 No Signature Found

   - 填不存在的 `nothing`：对话框说明它不是有效的版本，不关闭
   - 右键一个提交 → Compare “<短哈希>” to Revision…：对话框预填这个提交
   - ⌘2 下按住 ⌘ 选中两个提交：详情为 “2 commits selected”，下方是 Cherry-Pick 与 Compare（⌘0 看 HEAD 分支时是 Revert 与 Compare）；按住 ⌥ 时 Compare 换成 “Compare “<较新>” to “<较早>””。右键两个提交的 Compare 项同样随 ⌥ 换成反向
7. 导出：Repository → Export Revision… 默认填入所选提交，否则是 HEAD：
   - 不勾选 Create Archive，Export Files… 后在保存面板选 `$m7_exports/导出 exports`：得到 `history-<8 位哈希>` 目录，内容与那个版本的文件树一致
   - 勾选 Create Archive 再导出一次，得到同名的 `.zip`
   - Activity 记下这两次导出，导出期间可以取消；右键提交的 Export Files from “<短哈希>”… 打开同一个对话框

```sh
ls "$m7_exports/导出 exports"
unzip -l "$m7_exports/导出 exports"/history-*.zip | tail -3
```

8. 保存补丁：右键 “Fix \*star\* parsing in 解析器” → Save Patch for “<短哈希>”…：
   - 对话框的 Options 里有 Omit Prefixes；Save… 选择 `$m7_exports/导出 exports`，得到 `0001-Fix-star-parsing-in.patch` 这类名字的文件
   - 选中两个普通提交后 Save Patch for 2 Revisions…，按提交从旧到新编为 `0001`、`0002`
   - 按住 ⌥ 时菜单项换成 Quick Save Patch for “<短哈希>”，没有省略号：不弹对话框、不询问保存位置，沿用上次的 Omit Prefixes，把 `0001-Fix-star-parsing-in.patch` 直接存到 `history` 的仓库根目录，Working Copy 多出这个未跟踪文件；核对后执行 `m7_sh "rm '$m7_root/history/0001-Fix-star-parsing-in.patch'"` 删掉它
   - 勾选 Omit Prefixes 再把第一个补丁存一次，同名文件被替换，其中的路径没有 `a/`、`b/` 前缀：

```sh
grep -h '^diff --git' "$m7_exports/导出 exports"/*.patch
```

## 引用与远端管理

仍在 `refs`，HEAD 在 `main`。

1. 快进：右键 `release/1.x` → Fast-Forward “release/1.x”：落后徽标消失，工作区与 HEAD 不变。`main` 与上游一致，右键没有这一项。

```sh
m7_git -C "$m7_root/refs" rev-parse release/1.x origin/release/1.x
```

   两行相同。
2. 重命名远端分支：右键 Remotes 下的 `origin/release/1.x` → Rename “origin/release/1.x”…，对话框说明分支在它的远端上改名：
   - 填 `main`：显示远端上已有同名分支，Rename 不可用
   - 填 `release/1.y` 后 Rename：远端只剩新名字，本地的 `release/1.x` 随即带上跟踪错误的标记

```sh
m7_git -C "$m7_root/refs" ls-remote origin 'refs/heads/release/*'
```

3. 跟踪：右键 `release/1.x` → Tracking，子菜单分 Remote Branches 与 Local Branches 两组，最后一项是 Remove Tracking：
   - 选 `origin/release/1.y`：跟踪错误消失，两边一致
   - 选 Remove Tracking 后，再打开子菜单时这一项打勾，`m7_git -C "$m7_root/refs" config --local --get-regexp 'branch\.release'` 没有 `remote` 与 `merge` 两项；再选回 `origin/release/1.y`
   - 按住 ⌥ 把 Remotes 下的 `origin/feature/search` 拖到 `main` 上，落点显示 Track：`main` 改为跟踪它并显示超前与落后数。用 Tracking 子菜单改回 `origin/main`
4. 删除分支：右键 `spike/废弃` → Delete Branch，对话框说明要删除的分支，Options 里的 Force Deletion 不勾选，点 Delete：
   - 普通删除失败，询问写明 “These branches are not fully merged: spike/废弃. Delete them anyway?”，下方是 Git 原文
   - 点 Force Delete 后分支被删除
   - 右键 `release/1.x` → Delete Branch，勾选 Force Deletion 与 Delete Tracked Branch（说明写出 `origin/release/1.y`）：本地分支与远端分支一起删除，`ls-remote` 不再列出 `release/`
5. 重命名本地分支：右键 `topic/父分支` → Rename “topic/父分支”…，改为 `topic/子分支`：父分支关系随分支移动，`m7_git -C "$m7_root/refs" config --local --get-regexp spooky` 列出 `branch.topic/子分支.spooky-parent`。再改回 `topic/父分支`。
6. 父分支：右键 `feature/冲突` → Parent Branch → Set Parent Branch…，Parent 选 `main`：配置多出 `branch.feature/冲突.spooky-parent refs/heads/main`。再打开一次，对话框说明会替换当前的父分支。Parent Branch → Remove Parent Branch 只在设了父分支时可用；移除后再设回 `main`，[Branches Review](#branches-review-与自动归档) 一节还要用。
7. 新建分支：Repository → Create Branch ⌘B：
   - Starting Point 是可输入的组合框，列表是仓库里的引用；起点是分支时 Options 里有 Track Branch “main”
   - Options 里另有 Pin Branch 与 Parent Branch，父分支默认是起点分支，第一项是 None
   - 新建 `topic/空`，起点 `main`，勾选 Pin Branch，不勾选 Check Out Branch：它出现在 Pinned 分组，配置里有 `spooky-pinned` 与 `spooky-parent`
8. 标签：Repository → Create New Tag… ⇧⌘T：
   - Name 填已有的 `v1.0`：显示同名标签已存在
   - 勾选 Sign Tag、Message 留空：显示签名标签需要说明
   - 新建 `v1.2`，Revision 为 `main`，Message 为 `Release 1.2`，勾选 Sign Tag，Signing Key 用 Configured Key：`m7_git -C "$m7_root/refs" verify-tag v1.2` 显示 `Good "git" signature`
   - Repository → Publish Tag… 选 `v1.2` 与 `origin`：远端出现这个标签
   - 右键 `v1.2` → Delete “v1.2”…，勾选 Also Delete on Remote：本地与远端都没有了
   - 右键 `v1.1` → Push “v1.1” To…：Push Revision 对话框预填 `v1.1`，Ref Spec 填 `refs/tags/v1.1` 后推送；远端的 `v1.1` 仍是附注标签

```sh
m7_git -C "$m7_root/refs" ls-remote origin 'refs/tags/v1.*'
```

   输出里有 `refs/tags/v1.1^{}` 一行。
9. 远端：Repository → Add New Remote…：
   - Name 填 `bad name`：说明它不是有效的名称，Add Remote 不可用
   - Name 填 `backup`，Remote URL 填下面命令的输出：连接检查通过后加入，Remotes 下多出 `backup`

```sh
printf '%s\n' "$m7_root/镜像 mirror.git"
```

   - 右键 `backup` → Rename “backup”…，改为 `mirror`
   - 单击 `mirror`：General 分段列出 Name、Fetch URL、Push URL、Options 与两组 refspec，鼠标移到行上出现操作按钮
   - Push URL 点 Set 填同一个地址，再点 Unset，确认后推送重新使用获取地址
   - Fetch Refspecs 点 Add Refspec，填 `+refs/tags/*:refs/tags/*`；填 `bad refspec` 时显示它不是有效的 refspec。之后 Edit、Delete 这一条
   - 勾选 Skip on “Auto-Fetch” and “Fetch All”：`m7_git -C "$m7_root/refs" config --local --get remote.mirror.skipFetchAll` 输出 `true`；取消勾选
   - Branches 分段列出这个远端的分支名与提交哈希；`镜像 mirror.git` 是空仓库，这里为空
   - 右键 `mirror` → Delete “mirror”…，说明只从这个仓库移除远端、不改动远端上的仓库；确认后 `镜像 mirror.git` 仍在
10. 在浏览器中打开：右键 `web` → View “web” in Browser，默认浏览器打开 `https://example.invalid/spooky/refs`；对 `origin` 执行同一项，说明本机路径的远端没有网页。

## 同步与自动获取

仍在 `refs`。先在另一个工作区准备远端的变化：在 `origin` 上新建 `feature/远端`，再给一个不在任何分支上的提交打标签并只推送标签：

```sh
m7_sh "cd '$m7_root/other' && '$m7_root/git' switch -q -c feature/远端 main && '$m7_root/git' commit -q --allow-empty -m 'Remote only' && '$m7_root/git' push -q origin feature/远端"
m7_sh "cd '$m7_root/other' && '$m7_root/git' switch -q --detach main && '$m7_root/git' commit -q --allow-empty -m 'Tagged elsewhere' && '$m7_root/git' tag nightly-elsewhere && '$m7_root/git' push -q origin nightly-elsewhere && '$m7_root/git' switch -q main"
```

1. Repository → Fetch ⇧⌘F，Options 有 Prune Obsolete Remote Branches、Fetch Submodules 与 Fetch All Tags：
   - 只选 `origin`、不勾选任何选项：Remotes 下出现 `origin/feature/远端`；`m7_git -C "$m7_root/refs" tag -l nightly-elsewhere` 没有输出
   - 勾选 Fetch All Tags 再获取：Tags 下出现 `nightly-elsewhere`
   - 在另一个工作区删掉远端分支，不勾选 Prune 时 `origin/feature/远端` 仍在，勾选后消失：

```sh
m7_sh "cd '$m7_root/other' && '$m7_root/git' push -q origin --delete feature/远端"
```

   - 选 Fetch All Remotes：Activity 里只获取 `origin`，跳过设了 Skip on “Auto-Fetch” and “Fetch All” 的 `web`；单独选 `web` 获取时失败，错误详情是 Git 原文
2. 拉取：先执行 `m7_git -C "$m7_root/refs" config --local pull.rebase true`，再双击 `feature/search` 检出，Repository → Pull ⇧⌘P，不勾选 Use Rebase Instead of Merge：生成合并提交，不受仓库里 `pull.rebase` 的影响。Edit → Undo 撤销这次拉取不可用（菜单写明 Can’t Undo Pull），改为 Working Copy → Reset HEAD to Revision… 选 `HEAD~1`、Hard 回到拉取前；再勾选 Use Rebase Instead of Merge 拉取：历史变成一条线，超前 1、落后 0。最后 `m7_git -C "$m7_root/refs" config --local --unset pull.rebase`。
3. 推送钩子：放入必定失败的推送前钩子：

```sh
m7_sh "mkdir -p '$m7_root/refs/.git/hooks' && cp '$m7_root/pre-push' '$m7_root/refs/.git/hooks/pre-push'"
```

   - Repository → Push ⇧⌘U，Options 有 Push All Tags、Force Push、Recurse Submodules 与 Skip Hooks；不勾选 Skip Hooks 推送失败，错误里有 `pre-push rejected this push`
   - Repository → Sync… ⇧⌘Y：Sync HEAD 对话框说明先把所选远端分支的新提交拉进 `feature/search`，再推送本地提交；Remote Branch 选 `origin/feature/search`。同步失败，说明 “Sync stopped at “Push”. Completed steps: Fetch and Pull.”，Activity 的状态随步骤依次是 Fetching…、Pulling…、Pushing…
   - 勾选 Skip Hooks 再推送：成功，`feature/search` 与 `origin/feature/search` 一致
   - 删除钩子：`m7_sh "rm '$m7_root/refs/.git/hooks/pre-push'"`
4. 推送全部标签：Push 对话框勾选 Push All Tags：远端多出 `builds/nightly-1` 与 `builds/nightly-2`。
5. 变基：Working Copy → Rebase… ⇧⌘R，Branch 选 `main`：`feature/search` 的提交排到 `main` 之后，与上游分叉。
6. 安全强推：Repository → Force Push with Lease…，Branch 为 `feature/search`，Destination 为 `origin/feature/search`：
   - 对话框写出这次推送带上去与覆盖掉的提交数，状态是绿色的 “The remote branch is at the version this branch had before its history was rewritten.”；点 Force Push 成功
   - 再打开一次：两边是同一个提交，状态写明没有可推送的内容，Force Push 不可用
   - 在终端改写本地最新的提交，打开对话框，状态仍是绿色；对话框开着时让另一个工作区往远端推一个提交，再点 Force Push：

```sh
m7_sh "cd '$m7_root/refs' && '$m7_root/git' commit -q --amend -m 'Rank the search results (rewritten)'"
m7_sh "cd '$m7_root/other' && '$m7_root/git' fetch -q origin && '$m7_root/git' switch -q -C feature/search origin/feature/search && '$m7_root/git' commit -q --allow-empty -m 'Pushed during the dialog' && '$m7_root/git' push -q origin feature/search"
```

   推送被拒，错误详情里的 Git 原文是 `stale info`，远端仍是 “Pushed during the dialog”。
   - Fetch 之后再打开对话框：状态变为黄色，说明远端有 1 个本地从未包含的提交。点 Cancel，用变基拉取把它并进来
7. Push To：Repository → Push To…，Revision 填 `main`，Remote 选 `origin`，Ref Spec 填 `refs/for/main`：推送成功，`m7_git -C "$m7_root/refs" ls-remote origin 'refs/for/*'` 列出 `refs/for/main`。Ref Spec 填 `bad..name` 时推送失败，远端不变。右键非当前的 `feature/冲突` → Push “feature/冲突” To… 打开同一个对话框并预填它。
8. 按住 ⌥：
   - Repository 菜单的 Fetch、Pull、Sync、Push 换成 Quick Fetch ⌥⇧⌘F、Quick Pull ⌥⇧⌘P、Quick Sync ⌥⇧⌘Y、Quick Push ⌥⇧⌘U；Working Copy 菜单的 Merge 与 Rebase 换成 Quick Merge ⌥⇧⌘M 与 Quick Rebase ⌥⇧⌘R
   - 工具栏的 Fetch | Pull | Push、Sync 与 Merge | Rebase 的提示换成 “Quick …:” 开头的说明，点按直接执行，不打开对话框；松开 ⌥ 或切到别的 App 后复原
   - 快速操作沿用对话框里记住的选项，以 HEAD 的跟踪分支为对象。检出没有跟踪分支的 `topic/父分支` 后执行 Quick Push：说明没有上游，什么都不做；之后检出 `main`
9. 子模块：打开 `modules`：
   - Fetch 对话框勾选 Fetch Submodules：`m7_git -C "$m7_root/modules/lib" log --oneline -1 origin/main` 显示 “Library v2”
   - 在子模块里提交并更新父仓库记录的版本：

```sh
m7_sh "cd '$m7_root/modules/lib' && '$m7_root/git' merge -q --ff-only origin/main && printf 'v3\n' >> lib.txt && '$m7_root/git' commit -q -am 'Library v3' && cd .. && '$m7_root/git' commit -q -am 'Bump the library'"
```

   - Push 对话框勾选 Recurse Submodules、选 Verify submodules before push：推送失败，Git 原文说明子模块里的改动在远端找不到
   - 改选 Push submodule commits on demand：先推子模块再推父仓库，`m7_git -C "$m7_root/lib-other" ls-remote origin main` 与 `m7_git -C "$m7_root/modules/lib" rev-parse HEAD` 相同
10. 自动获取：Settings → General 的 Automatically fetch remote repositories 有 Never (only manually)、Every 5 Minutes、Every 10 Minutes、Every 30 Minutes 与 Every Hour，默认每 30 分钟。
    - 改为 Every 5 Minutes。在另一个工作区往 `main` 推一个提交后关闭并重新打开 `refs`：约 10 秒后 Activity 出现一条 Auto Fetch，`main` 显示落后 1，跳过 `web`

```sh
m7_sh "cd '$m7_root/other' && '$m7_root/git' switch -q main && '$m7_root/git' pull -q --ff-only && '$m7_root/git' commit -q --allow-empty -m 'Fetched automatically' && '$m7_root/git' push -q origin main"
```

    - 切到别的 App 超过 5 分钟，Activity 照常出现新的 Auto Fetch
    - 窗口显示仓库管理界面时不自动获取
    - 用 Quick Pull 把 `main` 拉到最新
11. 自动获取不询问凭据：启动要求登录的 HTTP 服务，加一个指向它的远端：

```sh
m7_sh "nohup perl '$m7_root/auth-server.pl' 18765 > /dev/null 2>&1 < /dev/null &"
m7_git -C "$m7_root/refs" remote add locked http://127.0.0.1:18765/locked.git
```

    - 关闭并重新打开 `refs`，约 10 秒后的 Auto Fetch 失败：不弹出任何输入框，失败只记在 Activity 里，原文是 Git 读不到用户名
    - 在 Fetch 对话框只选 `locked` 获取：弹出用户名询问，点 Cancel 后获取失败
    - 收尾：

```sh
m7_git -C "$m7_root/refs" remote remove locked
m7_sh "pkill -f '$m7_root/auth-server.pl'"
```

    - 把自动获取的间隔改回原来的设置

## 改写操作与交互式变基

打开 `rewrite`，按 ⌘0 看 HEAD 分支。先记下 `main` 的位置，后面的步骤做完后用它复原：

```sh
m7_head="$(m7_git -C "$m7_root/rewrite" rev-parse HEAD)"
m7_restore() { m7_git -C "$m7_root/rewrite" reset -q --hard "$m7_head"; }
```

1. 列表头下方有一条横幅 “Some commits on this branch are marked with fixup!, squash! or amend!.”，右侧是 Autosquash；搜索时与按 ⌘2 看全部历史时横幅不出现。
2. 反转：右键 “Tune the lexer” → Revert “<短哈希>”…，对话框 Revert Revision 说明会在 HEAD 上新建一个撤回改动的提交，Options 里勾选 Automatically commit reverted changes：HEAD 多出 “Revert "Tune the lexer"”。Edit → Undo Revert ⌘Z 撤销。
   - 按住 ⌘ 选中 “Add the formatter” 与 “Tune the lexer” → Revert 2 Revisions…，取消勾选自动提交：改动只出现在工作区，没有新提交。⌘Z 撤销后工作区干净
3. 摘取：侧边栏单击 `pick/合并`，右键 “Add a single fix” → Cherry-Pick “<短哈希>”…，对话框 Cherry-Pick Commit 有 Directly commit cherry-picked changes 与 Use fast-forward if possible：`main` 多出这个提交。
   - 右键 “Merge branch 'pick/extra'” → Cherry-Pick…：对话框多出 Mainline，选第一个父提交后执行，`main` 多出 `extra.txt`
   - 按住 ⌘ 同时选中这两个提交再摘取：说明合并提交只能单独摘取
   - ⌘Z 两次，`main` 回到原样
4. 重置：先在工作区留一处改动，再选 Working Copy → Reset HEAD to Revision…，Revision 填 `HEAD~1`：

```sh
m7_sh "printf 'local\n' >> '$m7_root/rewrite/parser.txt'"
```

   - 对话框列出离开当前分支的提交 “Add the formatter”，Mode 有 Soft、Mixed、Hard，各带一句风险说明，默认 Mixed
   - Soft：`formatter.txt` 留在暂存区，`parser.txt` 的改动不变；⌘Z
   - Mixed：`formatter.txt` 变为未跟踪；⌘Z
   - Hard：对话框另外提示工作区的改动会被丢弃；执行后工作区干净。⌘Z 后 “Add the formatter” 与 `parser.txt` 的改动都回来了
   - 最后 `m7_git -C "$m7_root/rewrite" checkout -- parser.txt`
5. 检出版本：Working Copy → Checkout Revision… ⇧⌘B，Revision 填 `v1.0`：对话框说明这不是本地分支，HEAD 会分离在它的提交上；检出后侧边栏的 Branches 显示 Detached HEAD。填 `pick/合并` 时没有这句说明，照常切换分支。最后双击 `main` 回去。
6. 变基到别处：Working Copy → Rebase Onto… ⌃⇧⌘R，Current Base 填 `v1.0`、New Base 填 `pick/合并`：
   - 对话框列出要移动的 4 个提交，Options 里有 Skip Hooks；New Base 填 `HEAD` 时说明新基点不能是 HEAD
   - 执行后 `main` 接在 `pick/合并` 之后，`single.txt` 与 `extra.txt` 都在；⌘Z
   - 右键 “Add the formatter” → Rebase “<短哈希>” Onto…：说明只把所选提交重放到新基点上，范围里没选的提交会从当前分支移除。New Base 填 `v1.0` 执行后，`main` 在 `v1.0` 之后只剩 “Add the formatter”；⌘Z
7. Autosquash：点横幅的 Autosquash，确认 sheet 列出会被改写的提交并标出 Fixup；确认后 “fixup! Add the printer” 并进 “Add the printer”，横幅消失。⌘Z。
8. 交互式变基的菜单项，每次做完执行 `m7_restore`：
   - 按住 ⌘ 选中 “Add the printer” 与 “Tune the lexer” → Squash 2 Revisions…：确认 sheet 说明两个提交的信息会合并，并列出被改写的提交；确认后两个提交合成一个
   - 同样两个提交 → Fixup 2 Revisions…：只保留目标提交的信息
   - 右键 “Tune the lexer” → Delete “<短哈希>”…：确认后它从 `main` 上消失
   - 把 “fixup! Add the printer” 拖到 “Add the printer” 上：落点旁显示 Squash，按住 ⌥ 换成 Fixup；拖到两行之间显示 Move Here。松开后都先出确认 sheet，这里点 Cancel
9. 改信息：右键 “Add the lexer” → Edit Commit Message of “<短哈希>”…：
   - sheet 预填原信息，下方列出从它开始会被改写的提交，已推送的提交带 Already pushed or merged 标记，并警告改写后本地分支与上游会分叉
   - 改为 `Add the lexer (reworded)`，正文写一行 `# note`，Save：弹出 M6 的注释询问，选 Remove Comments
   - `m7_git -C "$m7_root/rewrite" log --format=%s -6` 显示新标题，正文里没有注释行；`m7_restore`
10. 编辑：右键 “Add the printer” → Edit “<短哈希>”，确认说明会停在这个提交、把它的改动退回工作区：
    - 进行中操作横幅提示先提交退回的改动再点 Continue；工作区有改动时 Continue 不可用
    - 提交 `printer.txt` 后 Continue 可用，点它后变基完成，“fixup! Add the printer” 等后续提交依次重放
    - `m7_restore`
11. 并入暂存的改动：

```sh
m7_sh "cd '$m7_root/rewrite' && printf 'notes\n' > printer-notes.txt && '$m7_root/git' add printer-notes.txt && printf 'format more\n' >> formatter.txt"
```

    右键 “Add the printer” → Amend “<短哈希>”，确认说明把暂存的改动加进这个提交：完成后 `printer-notes.txt` 出现在 “Add the printer” 的变更集里，`formatter.txt` 的未暂存改动保留在工作区。`m7_restore`。
12. 改写前分支被移动：右键 “Tune the lexer” → Delete “<短哈希>”…，确认 sheet 开着时在终端追加一个提交，再确认：

```sh
m7_sh "cd '$m7_root/rewrite' && '$m7_root/git' commit -q --allow-empty -m 'Moved during the sheet'"
```

    报错 “The Branch Changed Before Rewriting”，说明什么都没有改写；`m7_restore`。
13. 工作区有改动时执行反转、摘取或交互式变基：按 Settings 里被本地改动挡住时的选项，先询问是否储藏，完成后恢复改动；Amend 不询问，由变基自己储藏其余改动。

回到 `refs`，HEAD 在 `main`。此时本地分支有 `bugfix/崩溃修复`、`feature/search`、`feature/冲突`、`feature/登录`、`old/实验`、`topic/父分支` 与 `topic/空`。

   - 第一行写出超前与落后的提交数，比较完成前显示 Comparing…；第二行是跟踪的远端分支与最后更新时间，`bugfix/崩溃修复` 显示红色的 Tracking branch is missing，没有上游的显示 No tracking branch

   - Stale 只剩 `old/实验`，Active 是其余全部
   - Tracking Error 只剩 `bugfix/崩溃修复`
   - Merge Conflicts 只剩 `feature/冲突`，Mergeable 是 `bugfix/崩溃修复`、`feature/search`、`old/实验` 与 `topic/父分支`

4. 选中 `feature/冲突`：详情头部是 “feature/冲突 → main”，旁边的冲突按钮写出 1 个文件，点开列出 `conflict.txt`；右端在 Commits 与 Changeset 之间切换，内容是从分叉点到分支顶端的比较。把基准换成 `feature/search`，各行重新比较；再换回 `main`。
5. 按住 ⌘ 选中两行：详情显示 “2 Branches Selected”；右键作用于整个选区。
6. 右键 `feature/冲突` → Resolve Merge Conflicts：检出 `feature/冲突` 并把 `main` 并进来，出现 M6 的冲突向导；点进行中操作横幅的 Abort，再双击 `main` 回去。
7. 批量归档：侧边栏底栏出现归档按钮，数量为 1。点开 Archive Branches：

   - 点 Archive：它移到 Archived Branches，侧边栏出现 “1 branch archived” 与 Undo；点 Undo 后回到 Branches
8. 自动归档：打开 Settings → General 的 Automatically archive obsolete branches，它与侧边栏视图设置、Archive Branches 对话框里的开关是同一个偏好。按 ⌘R 刷新：
   - 弹出同样的对话框，只列出 `old/实验`，说明这些分支即将被自动归档，可以取消勾选要保留的分支。点 Archive
   - Archived Branches 标题右侧出现圆点；在侧边栏选中 `old/实验` 停留片刻，圆点消失。再有自动归档的分支时，右键标题 → Mark All as Reviewed 一次清除
   - 一天之内再刷新不会再次询问
   - 把 `old/实验` 取消归档；右键它，勾选 Archive 菜单项下的 Skips Auto-Archiving，配置里多出 `spooky-skip-auto-archive`，之后的自动归档不再列出它；再取消勾选
   - 关掉自动归档
9. 与基准分支比较：侧边栏单击 `topic/父分支`，View → History → Compare Branches ⌃⌥⌘C（列表头的比较按钮同一个开关）：

   - 它自己的提交之后是一行 “Fork point of parent branch “main””，提交图照常穿过这一行
   - 窗口副标题为 “topic/父分支 → main (n Commits)”

   - 再按 ⌃⌥⌘C 关掉，列表回到普通的历史

    - Merge：检出 `topic/父分支` 并合并 `main`，按钮消失。⌘Z 回到之前的分支与位置
    - 改选 Rebase 再做一次，`topic/父分支` 的提交排到 `main` 之后；⌘Z

## Reflog 与撤销

仍在 `refs`。

1. View → Show Reflog ⌘6，副标题为 “Reflog (HEAD)”：
   - 表头的 Ref 菜单列出 HEAD 与本地分支，当前分支排在最前
   - 每行上方是短哈希、动作标记与日期，动作标记按命令着色，日期跟随日期格式；下方是记录的说明，最多两行
   - 选中一行，右侧显示这个提交的详情
   - 视图设置打开 Show Reflog 后，侧边栏 Workspace 的 Reflog 行打开同一个视图
2. 工具栏搜索框的占位是 Search for Reflog Message，输入 `checkout`：只剩切换分支的记录。
3. 停在这个视图，在侧边栏双击 `feature/冲突` 检出：HEAD 的记录随即重读，最上面是这次切换；再双击 `main`。
4. Ref 选 `feature/search`，副标题变为 “Reflog (feature/search)”。右键较早的一条（如变基之前的那条）：
   - Restore “feature/search” to “<短哈希>”…：确认写明把分支移到这个提交、不改动工作区与暂存区，离开分支的提交仍能在 Reflog 里找到；确认后分支的超前与落后数随之变化。⌘Z 撤销
   - Create New Branch from “<短哈希>”…：打开新建分支对话框，起点是这条记录的提交；新建 `recovered/search`
   - Cherry-Pick “<短哈希>”…、Reset HEAD to “<短哈希>”… 与 Save Patch for “<短哈希>”… 打开各自的对话框，这里点 Cancel
   - 把一条记录拖到侧边栏的 `main` 上，落点显示 Cherry-Pick，松开后打开摘取对话框；点 Cancel
   - Ref 选 `recovered/search`，再删除这个分支：视图回到 HEAD 的记录
5. 撤销与重做：
   - 在终端改一个文件，在 Spooky 里暂存并提交 “Undo test”：Edit 菜单是 Undo Commit ⌘Z。撤销后提交消失，改动回到暂存区；Redo Commit ⇧⌘Z 把提交放回来

```sh
m7_sh "printf 'undo\n' >> '$m7_root/refs/notes.txt'"
```

   - 再在终端改动工作区：Edit 菜单变为 “Can’t Undo Commit (Repository Changed)”，不可用；`m7_git -C "$m7_root/refs" checkout -- notes.txt` 之后恢复可用
   - 在另一个窗口（⌘N）打开 `refs`：两个窗口的 Edit 菜单显示同一个可撤销的操作，在一个窗口撤销后另一个随之变化。关掉这个窗口
   - 在终端开始一次会冲突的合并：Edit 菜单变为 “Can’t Undo Commit (Operation in Progress)”；中止合并后恢复

```sh
m7_git -C "$m7_root/refs" merge feature/冲突
m7_git -C "$m7_root/refs" merge --abort
```

   - Push 这个提交：Edit 菜单变为 “Can’t Undo Push”，之前的操作也不能再撤销
   - 在提交信息框里输入文字后 ⌘Z 撤销的是文字，不是仓库操作
   - 置顶、归档、快进、设置上游、本地分支改名、新建分支与标签、合并、变基、摘取、反转、重置、储藏与 Update Branch 都可以撤销；获取、拉取、推送、远端分支与远端设置的改动、提交身份、assume-unchanged 与忽略规则不能撤销，完成后 Edit 菜单写明 “Can’t Undo …”

## 右键菜单与拖放

1. 历史的右键菜单（`rewrite`）：
   - ⌘0 下右键单个提交：复制哈希之后依次是 Check Out、Reset HEAD to…、Revert…、Rebase … Onto…，Amend、Edit、Edit Commit Message of…、Delete…，Create New Branch from…、Create New Tag from…，最后是 Save Patch、Export Files 与 Compare
   - 选中两个提交：Revert 2 Revisions…、Rebase 2 Revisions Onto…、Delete 2 Revisions…、Squash 2 Revisions… 与 Fixup 2 Revisions…；检出、重置、新建分支与标签是灰色的通用项；比较一项直接写出两个短哈希
   - 侧边栏单击 `pick/合并` 后右键：中间一组只有 Reset HEAD to…、灰色的 Revert… 与 Cherry-Pick…，没有交互式变基各项
   - 按住 ⌥：Save Patch 换成 Quick Save Patch，两个提交的比较换成反向
2. 分支的右键菜单（`refs`）：
   - HEAD 分支 `main`：Push、Pull 与 Sync…，按住 ⌥ 换成 Quick Push “main” to “origin/main”、Quick Pull “origin/main” Into “main”、Quick Sync “main” with “origin/main”；Merge、Rebase… 与 Rebase Onto…，按住 ⌥ 换成 Quick Merge “origin/main” Into “main” 与 Quick Rebase “main” on “origin/main”
   - 非当前的本地分支 `feature/search`：Push 与 Push “feature/search” To…，合并只有 Merge
   - 没有跟踪分支的 HEAD 分支没有快速版本
   - 远端分支：Track Remote Branch 与 Pull，按住 ⌥ 换成 Quick Pull “origin/feature/search”
3. 拖放：
   - `rewrite` 侧边栏单击 `pick/合并`，把 “Add a single fix” 拖到 Working Copy 或 `main`：落点显示 Cherry-Pick，松开打开摘取对话框；按住 ⌥ 显示 Revert。多选两个提交一起拖，对话框是两个提交
   - 打开 “Add a single fix” 的详情，把变更集里的 `single.txt` 拖到 Working Copy：落点显示 Apply Patch，松开后只在工作区出现这个文件，暂存区不变；之后删除它
   - 按住 ⌥ 把本地分支 `pick/合并` 拖到 `main`：落点显示 Rebase，松开打开预选了它的 Rebase 对话框；点 Cancel
   - `refs` 里把一个提交或本地分支拖到 Tags 标题或 `builds` 文件夹：落点显示 Create Tag，松开打开预填了版本的新建标签对话框
   - 把 `bugfix/崩溃修复` 拖进 `feature` 文件夹：落点显示 Move Here，松开后直接改名为 `feature/崩溃修复`，跟踪配置随之移动；⌘Z 改回
   - 把标签 `v1.1` 拖到 Remotes 下的 `origin`：落点显示 Publish Tag，松开打开预选了 `origin` 的发布对话框；点 Cancel
   - 不支持的组合没有落点提示，松开后什么都不做

## 端到端流程

打开 `journey`，依次完成建分支 → 提交 → 标签 → Fetch → Pull / Rebase → Push → 安全强推 → Reflog 恢复：

1. ⌘B 新建 `feature/旅程`，起点 `main`，勾选 Check Out Branch。
2. 在终端追加一行，在 Spooky 里暂存并提交 “Add step three”：

```sh
m7_sh "printf 'step three\n' >> '$m7_root/journey/journey.txt'"
```

3. ⇧⌘T 新建附注标签 `journey-1`，说明为 `Journey 1`。
4. Repository → Publish Branch 发布到 `origin` 并跟踪；Repository → Publish Tag… 发布 `journey-1`。
5. 另一个工作区在远端分支上追加一个提交，本地再提交一次，形成分叉：

```sh
m7_sh "cd '$m7_root/journey-other' && '$m7_root/git' fetch -q origin && '$m7_root/git' switch -q feature/旅程 && printf 'from elsewhere\n' > elsewhere.txt && '$m7_root/git' add elsewhere.txt && '$m7_root/git' commit -q -m 'Add a step from elsewhere' && '$m7_root/git' push -q origin feature/旅程"
m7_sh "printf 'step four\n' >> '$m7_root/journey/journey.txt'"
```

   在 Spooky 里提交 “Add step four”。
6. ⇧⌘F 获取：`feature/旅程` 超前 1、落后 1。
7. ⇧⌘P 拉取，勾选 Use Rebase Instead of Merge：历史成为一条线，只超前 1。
8. ⇧⌘U 推送成功。
9. 用提交区的 Amend 把最新的提交改为 “Add step four (amended)”；普通推送被拒，错误详情是 Git 原文。
10. Repository → Force Push with Lease…：状态为绿色，Force Push 后远端与本地一致：

```sh
m7_git -C "$m7_root/journey" ls-remote origin refs/heads/feature/旅程
m7_git -C "$m7_root/journey" rev-parse HEAD
```

11. 双击 `main` 检出，⌘6 的 Ref 选 `feature/旅程`。最上面一条是 Amend，第二条以 `rebase (finish)` 开头，是 Amend 之前的位置；右键第二条 → Restore “feature/旅程” to “<短哈希>”…，确认后：

```sh
m7_git -C "$m7_root/journey" log -1 --format=%s feature/旅程
```

    输出 `Add step four`。Activity 按顺序记下每一步，失败的那次普通推送保留原文。

## 实现说明

- 历史搜索的同类条件之间是 “或”，不同类条件之间是 “且”；文字条件忽略大小写、按字面匹配，文件条件按字面匹配文件或目录，哈希前缀至少 4 位。日期条件按本地日历的整天比较提交人日期：之后从下一天开始，之前截止到前一天，区间包含两端。窗口副标题的提交数最多数到 50,000，数到上限时写 “or more”。
- 历史的视图设置、日期格式与合并 Diff 方式所有窗口共用，分别记在偏好 `historyShowGraph`、`historyShowFirstParentOnly`、`historySortByTopoOrder`、`historySortByDate`、`historyGrouping`、`historySmallRows`、`commitDateFormat` 与 `historyMergeDiffMode`。显示提交图时 Topo Order 总是勾选；Date 与 Topo Order 都勾选时按日期排序；日期分组只在按日期排序时生效。
- 回到历史时列表回到全部历史并清掉搜索条件；提交不在已加载的分页里时按每页 1,000 个续载；排在第 10,000 个之后时先询问，同意后才续载到它；不在当前历史里时说明找不到。
- 作者头像按邮箱去掉首尾空白、转成小写后的 SHA-256 向 Gravatar 请求，没有头像的邮箱返回 404；结果只在本次运行的内存里缓存，没有头像或请求失败时显示首字母。
- 合并提交的三种 Diff 方式对应 `--diff-merges=off`、`first-parent` 与 `combined`；组合 Diff 在只读视图里折成单列，任一父提交一侧为删除的行算删除行。
- 签名校验经包装器的 gpg 入口执行，校验时加 `--no-auto-key-retrieve --no-auto-check-trustdb`，不会去密钥服务器取钥。服务器仓库的 gpg 本来就配置为包装器；本机仓库为每次校验在 `/tmp/spooky-verify-*`（`0700`）里放一份包装器，校验结束即删除。
- 导出、归档与保存补丁是只读命令，不占用仓库写锁：`git archive` 与 `git format-patch --stdout` 的标准输出边读边写进 A 上的临时文件，不整份留在内存里，完成后替换目标，失败或取消时删除半成品。补丁按提交从旧到新编号，文件名与 `format-patch` 写进目录时相同；合并提交不存补丁。快速保存补丁是例外：在仓库所在的机器上执行 `git format-patch -o <仓库根目录>`，由 Git 直接写进仓库根目录，服务器仓库写在 B 上；它会写文件，按写操作经仓库队列排队。后缀与封面信固定为 `--suffix=.patch` 与 `--no-cover-letter`，仓库的 `format.suffix`、`format.coverLetter` 不改变文件名与个数，同名文件直接覆盖。
- 本地分支的置顶、归档、父分支与分支整理的标记写在仓库配置的 `branch.<名称>` 段，键名为 `spooky-pinned`、`spooky-archived`、`spooky-parent`、`spooky-skip-auto-archive` 与 `spooky-archive-review`；分支改名时随段移动，删除时随段清除。侧边栏的视图设置记在全局偏好，所有仓库共用。
- 基准分支是存在的 `main`、`master`、`develop`、`dev`、`next` 与各分支仍存在的父分支，它们不标陈旧，也不进归档建议。陈旧按顶端提交的提交时间判断，早于阈值月数之前才算；上游引用已不存在即为跟踪错误。归档建议只收陈旧的分支，以及托管服务上请求已合并、此后没有新提交的分支。
- 分支整理用 `merge-tree --write-tree` 预览能否并入基准；它会往对象库写入对象，按写操作经仓库队列排队。自动归档每个仓库每天最多检查一次，上次检查的时刻记在偏好 `autoArchiveLastCheck`。
- Fetch 使用 porcelain 输出；它不能与 `--recurse-submodules` 同用，获取子模块时在仓库本身获取之后执行 `submodule foreach --recursive git fetch`。获取全部远端时跳过设了 `remote.<名称>.skipFetchAll` 的远端，明确指定时照常获取。
- 自动获取的间隔记在偏好 `autoFetchInterval`，可选 0、300、600、1,800 与 3,600 秒，默认 1,800 秒；打开仓库 10 秒后第一次获取，之后每隔一个间隔。只在窗口显示仓库且仓库可写时进行，App 在后台也照常；它不询问凭据，只用钥匙串里已存的，取不到就按取消处理，失败只记进 Activity，也不进入撤销记录。
- 安全强推写明期望值：`--force-with-lease=refs/heads/<目标>:<期望的提交>`，期望值是对话框读到的远端跟踪分支，不依赖可能已被自动获取改动的跟踪引用。改写前的版本取本地分支 reflog 里最近一个不再是当前提交祖先的版本。Push To 的目标不以 `refs/` 开头时按分支名处理；推到 `refs/tags/` 时推送标签对象本身。
- 交互式变基的提交序列与信息由内联在命令里的编辑器写入，在仓库所在的机器上运行：执行前核对 HEAD 仍是计划时的提交，Git 给出的 todo 与计划不一致时编辑器以失败退出，变基中止、不改写任何提交。并入暂存改动先写一个树取自暂存区的 fixup 提交，再以 `--autostash` 变基。
- 撤销与重做按仓库记录，同一仓库开在几个窗口里时共用一份。每次可撤销的写操作前后各记一次 HEAD、`refs/heads` 与 `refs/tags`、各分支的配置段、储藏列表、索引写成的树（`write-tree`）与已跟踪文件的内容（`stash create`），快照建在仓库所在的机器上，A 只保存哈希；未跟踪文件只记路径。恢复前完整核对现状仍是记录时的状态，不一致、有进行中的操作或冲突、会覆盖找不回内容的未跟踪文件、assume-unchanged 文件有改动时都拒绝，不做任何改动。不能撤销的操作成功后清空这个仓库的撤销记录。
- 断线核对报告列出中断前后远端跟踪分支的变化，获取与推送可能已经部分完成；写入不重试。
