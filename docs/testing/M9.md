# M9：托管协作与仓库扩展验收

M9 承接 [M8](M8.md)，在本机与服务器仓库上交付以下能力，M1–M8 的验收步骤继续适用：

- github.com、GitLab.com 与私有部署 GitLab 的托管账号，Settings › Accounts 页
- Pull Request 与 Merge Request 的列表、详情、讨论、提交、改动、新建、修改、评论、关闭、合并与检出
- 发布仓库、提交信息里的 Issue 编号补全
- 分支整理接入请求状态、服务端合并识别与归档的审计记录
- 子模块、工作树与 Git LFS

## 自动验证

在仓库根目录执行：

```sh
mise run swift:lint
mise run build
mise run test
swift build --product Spooky
./scripts/build-app.sh
```

Git LFS 的测试只在 `PATH` 或 Homebrew 的目录里找得到 `git-lfs` 时运行，找不到时跳过并在测试结果里标出。

github.com 的实测默认跳过。准备一个专用的测试仓库（带一个提交的 `main`）与能读写它的令牌，然后：

```sh
SPOOKY_GITHUB_TESTS=1 SPOOKY_GITHUB_TOKEN=<令牌> SPOOKY_GITHUB_REPOSITORY=<owner/repo> swift test --filter GitHubLiveTests
```

- `GitHubLiveTests`：推送临时分支，新建 Pull Request，在列表里找到它，评论并读回，修改标题与描述，在本机从 `refs/pull/<编号>/head` 取回并检出成本地分支，等 GitHub 算完能否合并后压缩合并并删除源分支；另一个请求直接关闭，结束时删掉它的分支
- 本机 Git 经 `gh auth git-credential` 认证推送与获取，令牌只从环境变量传入

M9 新增的自动测试覆盖：

- 托管实例：私有部署地址的解析（端口、部署路径、去掉末尾的 “/” 与查询）；github.com 的 HTTPS、SSH、scp 与 `ssh.github.com` 写法；私有部署 GitLab 的 HTTPS 地址要端口与部署路径都一致，SSH 地址只比主机，组可以多层；SSH 别名的地址对应不上
- 托管接口：GitHub 的认证头与 API 版本，地址里没有令牌，不用缓存里的旧响应；GitLab 先查版本，低于 15.7 时不兼容；401、403、速率限制（带解除时间）、404、422、5xx、连不上、证书不受信任、TLS 握手失败与不兼容的响应各自分类并保留原文；`Link` 头分页；设备授权的等待、放慢、成功、拒绝与过期
- 请求：GitHub 的列表、Fork、草稿与网页地址；合并选项按仓库允许的方式、写权限与冲突；压缩合并带上源分支提交，再删除同仓库的源分支；从 Fork 新建时写成 `owner:branch`；GitLab 的多层路径转义、同一个 Fork 只查一次源项目、合并策略、必须压缩、项目规则拦下的合并、系统记录；不同项目的同号请求是不同的身份
- 仓库里的请求：克隆后取回请求的引用、比较基准；从 Fork 的请求新建不跟踪的分支，同名分支指向别处时拒绝，同仓库的请求跟踪远端分支
- 发布仓库与 Issue：GitHub 的所有者与在组织下新建，GitLab 的命名空间、可见性与是否已存在；GitHub 的 Issue 列表去掉 Pull Request
- 账号：账号写进偏好而令牌不在其中，同一实例同名的账号换令牌、清除重新认证的标记，不同用户名另加，移除时删除令牌，钥匙串拒绝写入时列表不变
- 请求视图：远端按手动关联、账号的实例与已知实例对应，多个账号要选，关联的账号被移除时当作没有关联；关联的存取；按服务的文案与格式参数
- 分支整理：有、没有打开着的请求两项筛选，不知道请求状态时都不满足；服务端已合并的分支即使不陈旧也进入归档建议
- Issue 补全：开关打开时识别 `#`，按编号前缀或标题筛选，插入 `#编号`
- 子模块：清单与状态、缺配置与缺指针、相对地址、添加与复用、初始化、更新与递归、同步、改地址与三个选项、获取与检出版本、移动、改名、删除与保留工作区、修复
- 工作树：新建检出分支与分离 HEAD、分支已被占用、从链接的工作树看当前工作树；删除与强制删除、移动；手动移走后失效、按新位置修复、目录已删时删除登记；清单的解析
- Git LFS：找不到 Git LFS 与版本低于 2.9.0 时报出能力缺失且不改动仓库；版本比较；仓库本地启用与钩子；含空格的模式与逐字文件名的写法，去掉规则后读回核对，认不出的规则报出仍然留着；推送、获取与拉取，强制输出的传输进度；带 LFS 的克隆换出内容

## 准备

### 本机

本机的测试目录放在系统临时目录下，测试结束后删除。Git 只读写这里的一份全局配置：

```sh
m9_root="$(mktemp -d "${TMPDIR:-/tmp}/spooky-m9.XXXXXXXX")"
mkdir "$m9_root/config"
export GIT_CONFIG_GLOBAL="$m9_root/config/gitconfig"
export GIT_CONFIG_NOSYSTEM=1
git config --global init.defaultBranch main
git config --global user.name 'Spooky Test'
git config --global user.email 'spooky@example.invalid'
git config --global commit.gpgSign false
git config --global protocol.file.allow always
```

测试仓库：

```sh
# 两个上游仓库，用作子模块
for name in 'lib 上游' other; do
  git init -q "$m9_root/$name"
  git -C "$m9_root/$name" commit -q --allow-empty -m "$name"
done

# 父仓库：一个已检出的子模块、一个没有初始化的子模块，两个分支
git init -q "$m9_root/父 仓库"
git -C "$m9_root/父 仓库" commit -q --allow-empty -m 'Start'
git -C "$m9_root/父 仓库" submodule add -q "$m9_root/lib 上游" 'libs/核心 lib'
git -C "$m9_root/父 仓库" submodule add -q "$m9_root/other" vendor/other
git -C "$m9_root/父 仓库" commit -q -m 'Submodules'
git -C "$m9_root/父 仓库" submodule deinit -q -f -- vendor/other
git -C "$m9_root/父 仓库" branch 'feature/登录'
git -C "$m9_root/父 仓库" branch release

# LFS 用的裸仓库与工作区
git init -q --bare "$m9_root/lfs.git"
git clone -q "$m9_root/lfs.git" "$m9_root/作品 仓库"
```

## 托管账号

1. 设置窗口的页签依次为 General、Appearance、Git Config、Text、Editor、Themes、User Profiles、Accounts、Integration、Environment、Updates。Accounts 是三列表格（Service、Instance、Username），没有账号时写 No Accounts；底部是 “+” 菜单（GitHub…、GitLab.com…、GitLab Self-Managed…）、“−” 与 Re-authenticate…。
2. GitHub… 的 Authentication 选 OAuth Access Token，Add Account：显示一次性验证码，复制到剪贴板并在浏览器打开验证页，下方是 Authorizing…；在浏览器里输入验证码并授权后，对话框关闭，表格多一行 github.com。在浏览器里拒绝授权时写明 Authorization Was Denied；等验证码过期时写明 The Code Has Expired。
3. 再选 Personal Access Token，填另一个账号的令牌：校验时写 Validating…，成功后同一服务有两个账号。填错的令牌：写明 The Token Was Rejected、修复方向与服务端原文（Bad credentials），列表不变。
4. GitLab Self-Managed… 填 `https://<实例>:<端口>/<部署路径>/` 与令牌：Instance 列写成 `主机:端口/部署路径`。实例低于 15.7 时写明 Incompatible API 与它的版本；地址错的主机写明 Can’t Reach the Hosting Service；自签名证书写明 The Certificate Isn’t Trusted。
5. 在托管服务上撤销一个令牌，然后打开它的请求视图：列表上方写明令牌被拒绝并有 Re-authenticate…，Accounts 里这一行标出 Needs re-authentication。选中它点 Re-authenticate…，换上新令牌后标记消失；换成另一个用户的令牌时写明 The Token Belongs to Another User。
6. “−” 先确认，移除后表格少一行。`security find-generic-password -s 'com.rakuyo.spooky.hosting.https://github.com'` 找得到还在的账号，找不到移除的账号；`defaults read com.rakuyo.spooky hostingAccounts` 里没有令牌。

## Pull Request 与 Merge Request

1. 打开测试仓库的克隆：侧边栏 Workspace 在 Stashes 之后有 Pull Requests；View › Show Pull Requests ⌘4、快捷操作的导航与 `spooky://open?repository=…&view=pullRequests` 都切到这里，后退、前进与窗口恢复记得这个视图。窗口副标题是 Pull Requests · <远端>。
2. 列表头部是 Remote 下拉、读取时的转圈与 “+”。列表每行三行：标题（草稿另有 Draft）、编号 · 作者 · 时间、源分支 → 目标分支（来自 Fork 时源分支前写出项目）。滚到最后一行时读取下一页。没有打开着的请求时写 No Pull Requests。
3. 远端换成一个不在支持服务上的地址：写明 Unsupported Remote 并有 Associate…；换成 GitLab.com 上的项目而没有 GitLab 账号：写明 No GitLab Account，Open Accounts 打开 Settings › Accounts。这时侧边栏、副标题与菜单都改叫 Merge Requests。
4. 选中一个请求：头部是编号、状态（Open、Draft、Closed、Merged）与 Conversation | Commits | Changeset 三段，底部是 Check Out、Close 与 Merge。Conversation 有标题、谁想把哪个分支合并进哪个分支、指派，描述（Markdown 行内格式；没有描述时写 No description given.）与 Edit…，评论，以及 Add Comment…。
5. Commits 与 Changeset 在仓库所在的机器上比较合并基准与源分支：源分支的提交还不在仓库里时写明 Commits Not Fetched，Fetch 从远端取回 `refs/pull/<编号>/head`（GitLab 是 `refs/merge-requests/<编号>/head`）后显示。
6. “+” 与 Repository › Create Pull Request… ⌃⌘P 打开新建对话框：Source 与 Target 各是远端（写出项目路径）与它的远端分支，Title 默认是源分支名，Description 多行。从 Fork 的远端新建时请求建在目标项目里。分支右键有 Create New Pull Request from “…”…；已有打开着的请求时换成 Show Pull Request for “…”。
7. Edit… 改标题、描述与目标分支，Save Changes 后列表与详情更新；Add Comment… 发表后评论出现在最后。Close 先确认，关闭后状态是 Closed。
8. Merge：GitHub 列出仓库允许的 Merge Type（Merge、Squash、Rebase）与 Delete Source Branch after Merge（默认按仓库设置）；GitLab 写出项目的 Merge Strategy，可以勾选 Squash Commits（项目要求压缩时不能取消）。没有合并权限、草稿、有冲突、项目规则不满足或还在计算时写明原因，Merge 不可用。合并后 Activity 记下服务端的说明与合并后的提交，随后在仓库所在的机器上 Quick Fetch 目标远端。
9. Check Out 填本地分支名（默认是源分支名）：同仓库的请求在远端跟踪分支正好是源分支提交时跟踪它；来自 Fork 的从提交新建；同名分支已指向别的提交时写明 The Branch Already Exists。工作区有改动挡住时按设置询问先储藏。

## GitLab 实例与项目识别

1. 私有部署实例的 HTTPS 远端带端口与部署路径、SSH 远端只写主机，都对应到同一个项目；多层 Group 的项目路径完整显示。
2. 远端写成 `~/.ssh/config` 里的别名：写明 Unsupported Remote；Associate… 选账号并填项目路径后，这个远端按关联读取，`defaults read com.rakuyo.spooky hostingAssociations` 记着远端地址到账号与项目。
3. 同一实例登录两个账号：写明 Choose an Account，选定的账号记在这个远端地址上。
4. 两个项目各有编号相同的 Merge Request：列表、详情与合并各自对应，互不混淆。
5. 实例连不上或证书不受信任时，已经读到的列表留在说明下面；速率限制写出解除的时间。

## 发布仓库

1. Repository › Publish Repository…（在 Publish Tag… 之后）：Account 选账号，Owner 列出账号本人与组织（GitLab 是命名空间），Name 默认是工作区的目录名，Description，Visibility（GitLab 另有 Internal），Remote Name 与 HTTPS | SSH，Remote URL 写出将要添加的地址与推送目标。
2. 同名仓库已在托管服务上时写明不会覆盖并禁用发布；本仓库已有同名远端时同样禁用。
3. 发布后托管服务上出现空仓库，本仓库多一个远端，当前分支推送过去并设为上游；Activity 记下新仓库的网页地址与推送的输出。

## Issue 补全

1. Settings › Editor 最下面有 Enable service integration plugins 与说明，默认勾选。
2. 在提交信息里输入 `#`：列出远端对应账号的项目里打开着的 Issue（编号与标题），输入数字或文字筛选，回车插入 `#编号`。GitHub 的列表里没有 Pull Request。
3. 取消勾选后输入 `#` 不再弹出补全；远端对应不上账号时没有候选，不显示任何 Issue 状态。

## 分支整理的协作状态

1. 把一个已压缩合并的请求的源分支提交建成本地分支：Branches Review 里这一行写出请求编号（已合并为紫色），批量归档的建议里也有它。
2. 筛选菜单另有 With Pull Request 与 Without Pull Request（GitLab 叫法是 Merge Request）。没有账号时选这两项，列表上方写明读不到请求状态，不把未知当成有或没有请求。
3. 归档与撤销归档后，Activity 的日志逐个写出分支被归档的原因：哪个请求已在哪里合并、最后更新的日期，或手动归档。

## 子模块

1. 打开 `父 仓库`：侧边栏 Submodules 分组列出两个子模块，没有初始化的另有标记，有本地改动的带数字；悬停写出名称与地址。单击打开子模块详情，双击在 Spooky 里打开子模块，工具栏最前面出现 Parent Repository，点按回到父仓库；没有父仓库时它隐藏。
2. 详情的 General | Shared Config | Local Config：名称、路径、本地改动数、检出的版本、指针、状态、生效的配置与三个选项；没有初始化时提示 Update，`.gitmodules` 的地址变了时提示 Synchronize。Shared 与 Local 两段可以改名、移动、改地址与三个选项，Default 删除这一项。
3. 右键子模块：Open、Checkout Revision ▸、Fetch / Update（按住 ⌥ 换成 Quick Fetch / Quick Update）、Initialize、Synchronize、Move、Rename、Delete。Repository 菜单有 Fetch Submodule… / Fetch All Submodules / Update Submodule… / Update All Submodules 与 Add New Submodule…。
4. 删除时 Keep Working Tree 只去掉配置；子模块有本地改动时询问 Force Delete。把 gitlink 留下、删掉 `.gitmodules` 的一段：详情写明 Invalid Submodule，Repair 重建配置。
5. Settings › General 的 Always update submodules automatically 打开时，检出、拉取或合并改了指针后直接更新子模块，关闭时询问；Always open submodules in Spooky 控制工作区里双击子模块的行为。

## 工作树

1. 侧边栏 Worktrees 分组列出其它工作树；分支右键 Add Worktree…，或把分支拖到 Worktrees 标题上新建。对话框的版本、目标目录（默认在仓库旁边）、Detach HEAD、Force 与 Open After Creation。
2. 分支已在别的工作树检出时，分支行带标记，不能在这里检出，右键改为打开那个工作树。
3. 工作树详情与右键：Open、Open in New Tab、Move…、Repair…（失效时）、Remove…（有改动时询问强制删除）。在终端里移走一个工作树目录：它显示为失效，Repair… 填新位置后恢复；目录删掉后 Remove 只删登记。
4. 在一个工作树里提交后，显示其它工作树的窗口随之刷新。

## Git LFS

1. 用 PATH 里没有 git-lfs 的方式启动 App（例如从 Finder 启动且没有勾选读取登录 shell 的变量）：仓库设置的 Git LFS 段写 Version: Not found 与修复方向；Working Copy 里 LFS ▸ Track This File 写明 Git LFS Is Unavailable 与 `git lfs version` 的原文，仓库不变。在 Settings › Environment 读取登录 shell 的变量后恢复正常。
2. 仓库设置的 Git LFS 段：Version 写出 Git LFS 的版本；没有启用时 Tracking Patterns 只有 Enable Git LFS，启用后是 Create Tracking Pattern 与 Open in Editor，每条规则有 Remove（先确认）。
3. Working Copy 右键在 Mark 与 Compare 之间有 LFS ▸：Track This File / Track N Files 逐字跟踪所选文件，Track All Files with Type “.psd” 跟踪同类型，Create Tracked File Pattern… 预填文件路径。`.gitattributes` 的改动留在工作区。
4. Repository 菜单在 Compare Revisions… 之后有 LFS ▸：Update、Fetch…、Pull…、Push…、Track…。推送、获取与拉取的进度写进 Activity。
5. 名字含方括号的文件逐字跟踪后在设置里 Remove：写明 Patterns Weren’t Removed 与那条规则，可以用 Open in Editor 手动删除。
6. 克隆时勾选 Use LFS Clone：克隆后的 LFS 文件是实际内容。

## 服务器仓库

1. 打开 `spooky-test` 上的仓库：子模块的添加、更新与获取，工作树的新建、移动与删除，Git LFS 的版本检查、启用、跟踪、获取、拉取与推送都在 B 上执行，凭据询问经中继回到本机。
2. 新建工作树时 Browse… 浏览 B 上的目录；B 上没有 Git LFS 时修复方向写明要把它加进非交互 SSH 会话的 PATH，并可在 Settings › Environment 检查 B 的 PATH。
3. 请求的检出、Fetch 与合并后的获取在 B 上执行；托管服务的接口从本机发出。
